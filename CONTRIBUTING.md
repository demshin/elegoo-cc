# Как помочь FAQ

Исправления и новые статьи принимаются через pull requests. Если решение ещё спорное или известен только один случай, начните с Issue: там можно собрать опыт сообщества и подтверждения.

## Что приложить к предложению

- Модель принтера: CC1, CC2 Carbon, CANVAS или общее для FDM. Укажите прошивку, слайсер, материал и настройки, если они влияют на результат.
- Симптомы, выполненные действия и сообщение об успешном результате. Совет «попробуй» сам по себе не подтверждает решение.
- Независимые повторные случаи. Продолжение одной истории, пересказ и пересылка не увеличивают их число.
- Ссылки на открытые обсуждения, документацию или обезличенные отчёты владельцев. Не прикладывайте чужую закрытую переписку, контакты и фотографии без разрешения.
- Ограничения: что не помогло, что изменили одновременно, можно ли отличить обход проблемы от устранения причины.

Доступ к закрытой выгрузке для участия не нужен. Архивные указатели в существующих статьях позволяют владельцу сверить выводы локально; исходная переписка не публикуется. Если у вас нет доступа к оригиналу, не выдавайте его за прочитанный источник.

В комментариях Issue участники уточняют условия, приводят дополнительные случаи и возражения. Итог со ссылками на основания переносится в связанный PR. Владелец принимает PR после проверки содержания и автоматических проверок; после merge сайт обновляется автоматически. Если подтверждений пока недостаточно, тема остаётся в Issues.

## Исправить или добавить статью

1. Создайте fork и отдельную ветку. Для небольшого исправления можно нажать «Редактировать страницу» внизу статьи на сайте.
2. Изменяйте исходный Markdown в faq/, а не генерируемое дерево сайта.
3. Для новой статьи добавьте файл в существующую тематическую папку и запись source/route/group в [список публикации](site/content-manifest.json). Счётчик на главной обновится при сборке.
4. Сохраните разделы для новичков и опытных, применимость, ограничения и ссылки на основания. Пишите по-русски, обычным языком печатника; термины должны помогать читателю.
5. Если добавляете изображение, проверьте право на публикацию и обезличивание. Поместите его в site/public/ и явно перечислите в assets списка публикации. Одного копирования файла в public/ недостаточно.
6. Выполните проверки ниже и создайте PR. Сошлитесь на Issue, если обсуждение велось там.

Обзоры тем и списки статей в них формируются автоматически из manifest. Заголовок берётся из H1, а применимость берётся из строки «Область» в статье. Кнопки «Добавить свой случай» и «Сообщить об ошибке» также добавляются сборкой; вручную вставлять их в Markdown не нужно.

Для сверки содержания действует [отдельная процедура](docs/article-review.md). Краткие заключения хранятся в site/article-reviews.json и привязаны к SHA-256 проверенного файла. Если меняете технический смысл статьи, прежнее заключение будет отмечено как устаревшее до повторной сверки. Отсутствие записи не означает отсутствие исходных оснований: ссылки на случаи остаются в статье.

## Локальные проверки без архива

Нужны Node.js 24 и Python 3. Команды из корня репозитория:

```sh
npm ci --prefix site
python3 scripts/check_docs.py --public
python3 -m unittest discover -s tests -v
npm --prefix site run build
python3 scripts/check_site.py
node scripts/check_site_search.mjs
npm --prefix site run preview
```

Для проверки именно адреса GitHub Pages задайте SITE_URL=https://demshin.github.io и SITE_BASE=/elegoo-cc в окружении сборки и обеих проверок готового сайта. [Подробности](site/README.md).

Проверки подтверждают структуру, ссылки, сборку и работу поиска. Они не доказывают правильность ремонта. Сообщения участников, официальные инструкции, гипотезы и собственные испытания обозначайте отдельно.

Команда python3 scripts/check_docs.py без --public дополнительно проверяет сообщения закрытого архива. Она предназначена только для локальной работы при наличии выгрузки в data/archive/; в публичном CI архив не используется.

Код проекта распространяется по [MIT](LICENSE), статьи и справочные тексты — по [CC BY-SA 4.0](LICENSE-CONTENT.md). Отправляя изменения, вы соглашаетесь распространять свой вклад по соответствующей лицензии и подтверждаете право его публиковать. Чужие документы и исходная переписка остаются под условиями их правообладателей.

ИИ можно использовать как помощника. Автор PR отвечает за проверку утверждений, ссылок и прав на материалы. Сырой архив, локальные скиллы, пароли и промежуточные данные не добавляются в Git и не передаются в CI.
