## Как добавить статью на сайт

Доступ к закрытому архиву не нужен. Статья добавляется обычным pull request: Markdown-файл с ответом и одна запись в списке публикации. После принятия PR сайт соберётся и обновится автоматически.

### 1. Соберите подтверждения

Проверьте, нет ли уже статьи о той же проблеме: существующую лучше дополнить. Для новой статьи нужны независимые повторные случаи и подтверждение успешного решения. Укажите модель принтера, прошивку, материал и другие существенные условия. Ссылки на открытые обсуждения, официальную документацию и обезличенные отчёты владельцев позволят проверить выводы.

Если известен только один случай или решение ещё спорное, [создайте Issue](https://github.com/demshin/elegoo-cc/issues/new/choose). В комментариях сообщество сможет добавить случаи и уточнения. Подробные требования к основаниям описаны в [правилах участия](CONTRIBUTING.md).

### 2. Создайте Markdown-файл

Сделайте fork репозитория и отдельную ветку. Добавьте файл в подходящую папку внутри faq/, например faq/slicing/new-issue.md. Имя файла пишите латиницей в нижнем регистре, слова разделяйте дефисами. Не редактируйте site/src/content/docs/: это временные файлы сборки.

За образец можно взять [статью об исправлении сетки модели](faq/slicing/model-mesh-repair.md). Минимальная структура:

```md
# Короткий заголовок: проблема и решение

Какие симптомы разбирает статья и что помогло в подтверждённых случаях.

**Область:** модель принтера, материал, прошивка и слайсер, если это важно.
**Обновлено:** ДД.ММ.ГГГГ.

## Для новичков

1. С чего начать проверку.
2. Что сделать и на что обратить внимание.

## Для опытных

Условия случаев, параметры, ограничения и попытки, которые не помогли.

## Проверка результата

Как убедиться, что способ помог, и когда нужно остановиться.

## Основания

Независимые случаи, подтверждённые результаты и ссылки на источники.
```

Отделяйте опыт участников от рекомендаций производителя и собственных предположений. Не переносите в статью закрытую переписку, чужие контакты и необезличенные вложения.

### 3. Включите статью в список публикации

В [site/content-manifest.json](site/content-manifest.json) добавьте объект в массив pages. Для файла из примера:

```json
{
  "source": "faq/slicing/new-issue.md",
  "route": "faq/slicing/new-issue",
  "group": "topic-3"
}
```

source — путь к исходному файлу от корня репозитория. route — уникальный путь страницы без начального слеша и расширения .md. group определяет раздел бокового меню:

| group | Раздел сайта |
| --- | --- |
| topic-1 | Материалы и подача |
| topic-2 | Первый слой и удержание детали |
| topic-3 | Слайсер, периметры и поддержки |
| topic-4 | Экструзия и нагрев |
| topic-5 | Механика, калибровка и обслуживание |
| topic-6 | Связь и интерфейс |
| topic-7 | Прошивки и восстановление работы |

Сохраните корректный JSON, включая запятые между соседними объектами. Статья появится в боковом меню автоматически; счётчик на главной тоже пересчитается. Для примера выше адрес будет https://demshin.github.io/elegoo-cc/faq/slicing/new-issue/.

В обзоре темы статья появится автоматически: заголовок и применимость берутся из её H1 и строки «Область». Добавьте ссылку в тематический список этого README. При необходимости дополните подборки «Новичку», «Опытному» и «По моделям» в site/: эти списки редактируются вручную. Ссылки между статьями пишите относительно исходных Markdown-файлов — сборка сама преобразует их в адреса сайта.

Кнопки обратной связи и блок оснований добавляются сборкой. Если для статьи есть отдельное заключение о сверке, оно хранится в site/article-reviews.json; изменение текста делает его устаревшим до повторной проверки. [Как сверять содержание](docs/article-review.md).

### 4. Проверьте сборку и откройте PR

Нужны Node.js 24 и Python 3. Из корня репозитория выполните:

```sh
npm ci --prefix site
python3 scripts/check_docs.py --public
python3 -m unittest discover -s tests -v
export SITE_URL=https://demshin.github.io
export SITE_BASE=/elegoo-cc
npm --prefix site run build
python3 scripts/check_site.py
node scripts/check_site_search.mjs
npm --prefix site run preview
```

Откройте адрес, который напечатает preview, с префиксом /elegoo-cc/. Проверьте новую статью, переходы по ссылкам и её наличие в поиске. Сырой архив для этих команд не требуется. [Подробнее о локальной сборке](site/README.md).

Создайте PR из своей ветки в main основного репозитория. Опишите изменение, приложите основания и ссылку на Issue, если обсуждение велось там. GitHub Actions проверит PR; после обсуждения и merge сайт опубликуется автоматически. Если проверки не запускались, прямо укажите это в PR — содержание статьи всё равно требует отдельной проверки по источникам.

## Как читать подтверждения

В FAQ попадают повторяющиеся проблемы, для которых есть явное сообщение об успешном решении. Повторные сообщения одного владельца и пересказы не увеличивают число независимых случаев. Успешный обход может восстановить работу, не устранив первопричину; такие ограничения отмечены в статье.

Повторяемость симптома и число успешных испытаний способа учитываются отдельно. Например, для неровностей предпросмотра найдены два независимых успешных изменения нарезки; это не объявлено двумя успешными физическими печатями.

Сообщения участников, рекомендации производителя и редакционные выводы разделены. Аппаратная проверка этих решений на принтере при подготовке FAQ не проводилась.
