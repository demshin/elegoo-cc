# Локальный статический сайт

Astro7.4.4 + Starlight0.42.8, русский интерфейс и локальный поиск Pagefind. Зависимости закреплены в package.json и package-lock.json. Для воспроизводимой сборки используйте Node.js 24 и Python 3. Минимальная версия Node для установленного Astro — 22.23.4.

## Сборка и просмотр

Из директории `site/`:

```sh
npm ci
npm run build
npm run preview
```

Для разработки: `npm run dev`. Печатный адрес сервера доступен только на локальном компьютере. Результат сборки находится в `site/dist/`.

## Содержимое и приватность

[content-manifest.json](content-manifest.json) задаёт явный список статей, семь тематических групп и публичные маршруты. Markdown в [faq/](../README.md) остаётся каноническим; генерируемое дерево `src/content/docs/` не редактируется вручную.

Счётчик на главной пересчитывается при подготовке содержимого: он учитывает только статьи из `faq/`, включённые в manifest. Чтобы новая статья появилась на сайте и в счётчике, добавьте её в manifest и пересоберите сайт. Формы «статья», «статьи» и «статей» выбираются автоматически.

Карточки главной и пункт «Все статьи темы» ведут на обзоры в topics/. Их исходные вводные находятся в site/topics/, а списки собираются из manifest: H1 статьи и её строка «Область». Обзор не требует ручного дополнения при добавлении новой статьи в существующую группу.

Внизу каждой статьи FAQ сборка добавляет закрытый блок «Источники и проверка» с основаниями и статусом текущей редакции. Под ним находятся ссылки на формы GitHub Issues с уже заполненными адресом статьи и условиями. Формы сами ничего не отправляют. Для обычной локальной сборки ссылки указывают на опубликованные статьи; при явных SITE_URL/SITE_BASE используется заданный адрес.

Краткие результаты сверки берутся из [article-reviews.json](article-reviews.json). Дата фактической сверки сохраняется. Если после неё менялась только подача и отдельный проверяющий сопоставил полные тексты, editorial_review связывает хеш исходника и новой редакции; дата этого сравнения показана отдельно. Несовпадение текущего SHA-256 с проверенной редакцией помечает заключение как устаревшее; отсутствие записи не создаёт отметку о выполненной проверке. [Процедура сверки](../docs/article-review.md). Подробные локальные отчёты и скилл остаются вне Git.

Список assets в manifest задаёт разрешённые файлы из site/public/. Неизвестный файл или symlink останавливает подготовку. Ссылка «Редактировать страницу» ведёт на исходный файл в GitHub, а не на генерируемую копию.

[Подготовка](../scripts/prepare_site.py) читает только разрешённые публичные файлы, добавляет метаданные, переписывает внутренние ссылки и превращает ссылки на исходный чат в текстовые номера сообщений. Цели архивных ссылок не открываются. Неизвестная ссылка, приватный источник или symlink останавливают подготовку до замены предыдущего дерева.

Сырые данные, вложения, локальные журналы и индексы не входят в сборку. Реестры оснований доступны читателю, но исключены из поиска. Указатели на закрытую переписку не обещают доступ к оригиналу.

## Проверки

Из корня проекта:

```sh
python3 scripts/check_repository.py
python3 scripts/check_docs.py --public
python3 -m unittest discover -s tests -v
python3 scripts/check_site.py
node scripts/check_site_search.mjs
node --test tests/site-behavior.test.mjs
```

Проверяются покрытие manifest, ссылки/якоря, отсутствие архивных файлов и запросы к реальному поисковому индексу без сети. 03.11.2026 локально проверены поиск, пустая выдача, следующие результаты, Escape/Ctrl+K, возврат фокуса и события кликов в отдельном headless Chrome. Вёрстка осмотрена при 1280×900 и при эмуляции экрана 390×844; это не проверка на физическом телефоне. События проверялись через заглушку gtag, без отправки в рабочую GA4.

Поиск понимает несколько распространённых формулировок: «не липнет», «сопли», «не тянет пластик», «отрывает углы», «поддержки не снимаются», а также «канвас» и слитные коды вроде «ошибка103». Правила находятся в src/lib/search-policy.mjs; введённый текст в поле не меняется. Это подбор статей по симптому, без определения причины неисправности. Проверка индекса проверяет ожидаемые статьи в первых трёх результатах, а не только наличие любой выдачи.

check_docs.py --public проверяет архивные указатели по формату, не открывая закрытую выгрузку. Без --public дополнительно проверяются сообщения и якоря локального архива в data/archive/. Этот путь можно сделать локальной ссылкой на папку своей выгрузки внутри data/. Содержимое data/ не добавляется в Git и не передаётся в CI.

## Подготовка для GitHub Pages

Целевой адрес — https://demshin.github.io/elegoo-cc/. Это отдельный project site; настройки существующего demsh.in и DNS не используются. Workflow в .github/workflows/pages.yml проверяет PR и публикует только после merge или push в main. В настройках Pages выбирается GitHub Actions; Custom domain остаётся пустым.

Проверка такого варианта:

```sh
export SITE_URL=https://demshin.github.io
export SITE_BASE=/elegoo-cc
npm --prefix site run build
python3 scripts/check_site.py
node scripts/check_site_search.mjs
npm --prefix site run preview
```

После этого preview открывается по напечатанному адресу с префиксом /elegoo-cc/. Для возврата к локальной сборке в корне выполните unset SITE_URL SITE_BASE и пересоберите сайт.

Для выкладки нужен только site/dist/; исходное и временное дерево не являются артефактом сайта. [Правила участия](../CONTRIBUTING.md), [план публикации](../docs/publication-plan.md).

## Аналитика посещаемости

Google Analytics 4 подключается через gtag.js тем же способом, что и на demsh.in. Перед сборкой нужно задать PUBLIC_GOOGLE_ANALYTICS_ID — публичный идентификатор потока вида G-XXXXXXXXXX. Он не является паролем; доступ к аккаунту Google для подключения тега не нужен. [Инструкция Google](https://developers.google.com/tag-platform/gtagjs).

В workflow GitHub Pages задан существующий счётчик demsh.in — G-XKK8ZMW7D2. Статистика собирается в тот же ресурс GA4. Для FAQ используйте фильтр по хосту demshin.github.io и пути, начинающемуся с /elegoo-cc/. Чтобы собирать её в другой поток, замените PUBLIC_GOOGLE_ANALYTICS_ID в workflow.

Без этой переменной внешний тег Google и инициализация GA4 не попадают в HTML. Обычная локальная сборка и preview не отправляют просмотры или события в GA4. Если явно задать ID при локальной сборке, аналитика будет включена и в её результате.

Тег добавляется один раз на каждую страницу, включая статьи и страницы источников. Для просмотра статистики нужен доступ к соответствующему ресурсу Google Analytics. Наличие тега в HTML само по себе не подтверждает приём событий: это проверяется через Tag Assistant или отчёт реального времени в GA4.

### События полезности

| Событие | Когда возникает | Параметры |
| --- | --- | --- |
| faq_search | Показана выдача после паузы во вводе | result_count, query_length, query_intent |
| faq_search_empty | Выдача пуста | query_length, query_intent |
| faq_search_result_click | Нажата ссылка результата | result_position, destination_path, query_intent |
| faq_feedback_click | Нажата кнопка обратной связи | feedback_type (case/correction), article_path |

query_intent — одна из фиксированных категорий: adhesion, stringing, extrusion, warping, supports, error_code, other. Исходный поисковый текст не передаётся; код ошибки тоже не включается в параметры запроса. Параметры путей содержат только публичный pathname без query string и якоря. Событие обратной связи означает переход к форме, а не отправленную Issue или подтверждённое решение. Событие поиска считается после паузы во вводе, поэтому несколько промежуточных запросов одного человека могут дать несколько событий.

В GA4 удобно смотреть три показателя, отфильтровав хост demshin.github.io и префикс /elegoo-cc/:

- Долю пустой выдачи: количество faq_search_empty / количество faq_search.
- Переходы из поиска по категориям и статьям: faq_search_result_click с query_intent и destination_path. Отношение кликов к поискам — вспомогательная метрика: один запрос может привести к нескольким кликам.
- Кнопки обратной связи по статьям: faq_feedback_click с feedback_type и article_path. Это помогает найти статьи, вызывающие вопросы, но не измеряет число исправлений.

Для разбивки в отчётах создайте пользовательские параметры уровня события (event-scoped custom dimensions) для query_intent, destination_path, feedback_type и article_path. result_count, query_length и result_position при необходимости зарегистрируйте как пользовательские метрики. Принятые события и параметры проверяются в Realtime/DebugView; пользовательские определения нужны для последующих отчётов. [События Google](https://developers.google.com/analytics/devguides/collection/ga4/events), [пользовательские параметры и показатели](https://support.google.com/analytics/answer/14240153).

Тесты вызывают локальную заглушку gtag и не отправляют события в рабочий ресурс. Они проверяют состав параметров и отсечение произвольного текста. Доставку до GA4 они не подтверждают. Для проверки после публикации откройте сайт без блокировки аналитики, выполните поиск с результатами и без них, перейдите к статье и нажмите кнопку обратной связи; затем сопоставьте эти события с Realtime или Tag Assistant. Если доступного подключения к GA4 нет, приём остаётся непроверенным.
